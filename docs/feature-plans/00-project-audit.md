# Project Audit

## Tech Stack Detected
- Frontend framework: React 19 with Vite 7.
- Backend framework: Spring Boot 3.4.4 with Java 17.
- Database: MongoDB through Spring Data MongoDB.
- Authentication method: custom bearer-token flow generated by `TokenService`, email OTP signup/reset, Google ID token login, frontend Zustand session persistence in localStorage.
- Styling system: Tailwind CSS 4 plus project CSS modules in `src/styles/`, design tokens in `src/styles/tokens.css`, theme context in `src/theme/themeContext.jsx`.
- State management: Zustand stores in `src/store/authStore.js` and `src/store/sheetStore.js` with slice files under `src/store/sheetStore/`.
- API structure: frontend modules in `src/api/`; backend REST controllers under `backend/src/main/java/com/iqms/backend/controller`, `backend/src/main/java/com/iqms/backend/profile`, `backend/src/main/java/com/iqms/backend/notification`, and `backend/src/main/java/com/iqms/backend/sheet`.
- Build tools: Vite, npm scripts, Vitest, ESLint on frontend; Maven on backend.

## Current Project Strengths
- The core sheet tracker is already broad: nested sheets, progress, import/export, public sheets, sharing, premium limits, and attempt logging are present.
- Backend is not a toy API. It includes auth, profiles, collaboration, notifications, premium, platform stats, and tests for some business services.
- Public profile and coding platform aggregation are already wired into the product.
- Design tokens and reusable UI components exist, so UI cleanup can be incremental.
- Test coverage exists across important frontend services and backend sheet/premium/collaboration services.

## Current Project Weaknesses
- Some backend packages and file paths are inconsistent, especially the sheet module path/package split under `backend/src/main/java/com/iqms/backend/sheet`.
- The most important domain payload, sheet topics/subtopics/questions, is stored and processed as raw maps.
- Several features are backend-first and lack full UI surfaces, especially teams, comments, and collaboration dashboards.
- Platform connectors run synchronously through external APIs/scraping and need production safeguards.
- Analytics are split between client calculations and platform snapshots rather than a clear analytics domain.
- Custom auth token handling should be hardened before production.
- Existing docs describe many APIs, but not all feature dependencies and implementation order.

## Risk Areas
- Editing `Sheet` structure can break import/export, reminders, analytics, public copies, premium limits, and frontend state normalization.
- Changing auth/token behavior can break every protected endpoint because the app uses a custom interceptor flow.
- Platform stats changes can break public profile payloads and `/add_accounts`.
- Profile payload changes can break both `ProfilePage.jsx` and `SharedPage.jsx`.
- Notification hydration parses nested sheet maps and attempt logs; schema changes need migration handling.
- Premium limit logic is duplicated across frontend expectations and backend enforcement.
- Existing dirty/generated files should not be reverted accidentally.

## Recommended Development Order
1. Stabilize contracts and tests: document current API payloads, ensure frontend build/tests and backend Maven tests can run reliably in the target Java version.
2. Harden core sheet schema: introduce typed DTO validation while preserving compatibility with existing documents.
3. Finish coding profile reliability: connector health, retry/backoff, background sync, typed stat snapshots.
4. Make attempt logs first-class: separate API/collection or typed embedded model with migration.
5. Add backend analytics snapshots after attempt logs and sheet schema are stable.
6. Productize collaboration UI only after permissions and core sheet contracts are stable.
7. Add AI and advanced recommendations after analytics data is reliable.
